# Лабораторная работа 6

## Роутинг, общее состояние и кеш запросов в React

Продолжите **свой проект из лабораторной №5**. Добавьте страницы, общее клиентское состояние и кеш серверных данных. Книги из лекции — пример: используйте товары, фильмы, задачи или другие сущности своей темы.

**Основной стек:** React Router, Redux Toolkit, React Redux и RTK Query. Дополнительный вариант на Zustand + TanStack Query реализовывать не требуется.

Установка: `npm install react-router @reduxjs/toolkit react-redux`.

Срок сдачи назначает преподаватель. Критерии накопительные: оценка 4 включает все условия на 3, оценка 5 — все условия на 4.

## Удовлетворительно — 3

- **Маршруты:** работают три страницы — список объектов, детали по динамическому `id` и отдельная страница выбранных объектов. Есть переходы через `Link` или `NavLink` без перезагрузки документа.
- **Общее состояние:** Redux store создан один раз вне переключаемых страниц и подключён через `Provider`. `createSlice` хранит корзину, избранное или другой клиентский выбор. Есть действие добавления; минимум два компонента используют эти данные через `useDispatch` и `useSelector`.
- **Переходы:** выбор сохраняется при смене страницы. Сохранение после полной перезагрузки браузера не требуется.
- **API и кеш:** минимум один список загружается реальным HTTP-запросом через RTK Query. Подключены `createApi`, его reducer и middleware; компонент использует сгенерированный query-хук.
- **Отображение:** показаны первая загрузка, сообщение об ошибке и успешный список со стабильным `key`.

**На защите:** добавьте объект, покажите общий счётчик, перейдите на другую страницу и загрузите данные API. Объясните, где хранится клиентский выбор и где — ответ сервера.

## Хорошо — 4

Выполнены все условия на 3, а также:

- **Навигация:** общая шапка и страницы организованы через layout и `Outlet`. Неизвестный путь и неизвестный `id` показывают понятное сообщение. Работают «Назад» и «Вперёд» браузера.
- **Прямая ссылка:** детали открываются по скопированному адресу и после обновления страницы. Для GitHub Pages подходит `HashRouter`; для `BrowserRouter` хостингу нужен fallback на `index.html`. Проверьте базовый путь ресурсов в подпапке.
- **Управление выбором:** можно убрать объект или изменить его количество. Все потребители сразу видят результат. Счётчики и суммы вычисляются из исходных данных, без независимых копий одного значения в нескольких `useState`.
- **Состояния запроса:** после ошибки доступен повтор без перезагрузки; успешный пустой ответ имеет отдельное сообщение. Первая загрузка и фоновое обновление различаются через `isLoading`/`isFetching`; при обновлении прежние данные остаются видны.
- **Проверка кеша:** покажите два компонента с одинаковым endpoint и аргументом либо возврат к использованному списку. По вкладке Network объясните, когда используется кеш и когда отправляется запрос. Ответ API не копируется вручную в отдельный slice.

**На защите:** дополнительно покажите ошибку → повтор → результат, пустой список и повторное использование кеша. Объясните, почему другой `id` может означать другую запись кеша.

## Отлично — 5

Выполнены все условия на 4, а также:

- **Изменение данных:** форма или действие отправляет RTK Query mutation, например меняет цену, название или статус. HTTP-метод соответствует вашему API (`POST`, `PUT` или `PATCH`).
- **Валидация:** некорректное значение не отправляется. Например, цена — конечное число не меньше нуля; пустое поле не превращается незаметно в ноль.
- **Результат сохранения:** виден статус ожидания, повторная отправка временно недоступна. Ошибка показана пользователю, после неё можно повторить попытку. Успех проверяется по результату запроса; для `try/catch` с mutation trigger используйте `.unwrap()`.
- **Обновление кеша:** query endpoints используют `providesTags`, успешная mutation — `invalidatesTags`. Новые данные появляются без перезагрузки. Проверьте и список, и детали, если у них отдельные endpoints.
- **Разделение данных:** черновик формы остаётся локальным, клиентский выбор хранится в своём slice, ответы сервера — в RTK Query. После изменения другие экраны не показывают вручную сохранённую старую копию.

**На защите:** покажите изменение → mutation → успешный ответ → обновление затронутых query → новый результат. Затем воспроизведите ошибку сохранения и повтор. Объясните, что invalidation делает с активной и неиспользуемой записью кеша. Общего тега для сущности достаточно; точечные теги и оптимистические обновления не обязательны.

## API для оценки «5»

Используйте источник, который сохраняет изменения и возвращает их последующим GET-запросом. Если публичный API только имитирует запись, можно подключить небольшой локальный **HTTP-сервер**, сохраняющий данные хотя бы на время запуска. Отдельная серверная платформа, база данных и авторизация не требуются. Локальный массив с Promise вместо HTTP-запроса не заменяет подключение API в лабораторной.

**Готовый вариант:** возьмите папку `lab-api` из материалов лекции. В ней [server.mjs](lab-api/server.mjs), [books.json](lab-api/books.json) и [инструкция](lab-api/README.md). Сервер уже написан; разрабатывать backend не нужно. Запустите `node lab-api/server.mjs`, а в `fetchBaseQuery` укажите `baseUrl: 'http://127.0.0.1:4191/api/'`. React-приложение запустите во втором терминале. Данные сохраняются до перезапуска; инструкция содержит способы показать ошибку, пустой ответ и повтор. Для своей темы можно заменить данные в `books.json`, сохранив поля `id` и `price`.
